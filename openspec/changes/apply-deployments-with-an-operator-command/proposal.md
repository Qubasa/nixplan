## Why

There is no way to build a plan's artifacts or put them on a machine except by writing the code that
does it. Every end-to-end folder writes its own: `tests/e2e/wired-pair/artifacts.nix` (89 lines),
`tests/e2e/portable-image/artifacts.nix` (75) and `tests/e2e/secret-delivery/artifacts.nix` (67) each
apply the folder's deployment to real packages, call `mkPlan`, call a realiser once per placed entry,
serialise the plan and collect the results into a link farm. The four steps are the same four in all
three files. `flake-module.nix:110-153` then imports each one by hand and writes two environment rows
per folder so pytest can find the output.

The consequence is that the machine layer proves less than it appears to. What each folder delivers is
what its own builder assembled, so a defect in the step between "plan" and "bytes on a machine" cannot
fail a test: there is no shared step to be defective. The same holds on the delivery side, where
`tests/e2e/delivery.py:179-338` owns `copy_argv`, `install_argv`, `deliver`, `deliver_value`,
`activate`, `status` and `rollback` — the operator's steps, in the right order, assembled by the
harness. `apps.planner-e2e` (`flake-module.nix:256`) is the only application this flake exposes, and
it runs tests.

For a reader outside this repository the gap is larger: `lib/` produces a plan, `image/` and
`flakelet/` each realise one entry of one plan, and nothing composes them. A user who wants what the
three folders demonstrate has to write a fourth `artifacts.nix`, and the in-flight
`generate-values-with-nixos-secrets` change is already scheduled to write it (its tasks 1.3 and 1.5,
both unchecked).

## What Changes

- **A fourth layer, `operator/`, builds a whole deployment.** `operator/read.nix` is the pure reading:
  which placed entries exist, which realiser and confinement profile each is stated to use, the
  artifact name each plan key projects onto, and every way that is refused. `operator/default.nix` is
  derivations over that reading: `plan.json`, `manifest.json`, one artifact per placed entry, in one
  link farm. This is the generic form of what the three `artifacts.nix` files hand-write, and the
  split mirrors `image/` and `flakelet/`, where `read.nix` is the whole reading and everything else is
  derivations over it.
- **`manifest.json` is the interface between the evaluating side and the tool.** It maps each plan key
  to the artifact built for it, the realiser that built it, the machine and address it goes to, and
  the units it declares; and each value entry to its files, their paths and its delivery set. A
  consumer of a deployment build reads the manifest and the plan, and nothing else. Artifacts are
  addressed by plan key, never by a name a folder chose: two keys projecting onto one artifact
  directory is an error, not a silent overwrite.
- **A build refuses an inapplicable deployment.** `mkPlan` already answers `applicable`
  (`lib/default.nix:115`) and `render` already prints the table (`:72`). `operator/` is where those two
  facts become a refusal, in the same posture as the realisers: a fact the entry does not record is a
  refusal naming the entry and the field, never a default.
- **`planner`, the operator's command, in `cli/` and nowhere else.** One binary, five subcommands:
  `plan` (evaluate and print the plan, or the diagnostics table and exit non-zero), `build` (realise a
  deployment build and report what it holds), `apply` (copy each artifact to its machine, write the
  generated values it is given, activate or attach each entry, in an order derived from the plan),
  `status` and `rollback`.
- **The command is its own flake module.** `cli/flake-module.nix` holds `packages.planner-cli` and
  `apps.planner` and is imported by `flake.nix` beside `./flake-module.nix` and `./devshells.nix`.
  The root module gains no line about the command: the two things `operator/` and `cli/` are — an
  evaluation the unit suite reads and a program with an interpreter closure — are separate
  deliverables, and deleting the command is deleting one directory and one import.
- **Generated bytes reach `apply` from outside the plan.** `apply --values <dir>` reads
  `<dir>/<entry-key>/<file>` and writes each file to the machines the entry's `delivery` set names, at
  the path the entry records, outside the store. A file the plan names and the source does not hold is
  refused before anything is dialled; so is a file the source holds and the plan does not name. What
  generates those bytes is not this change: the directory is the seam
  `generate-values-with-nixos-secrets` fills.
- **BREAKING — the three `artifacts.nix` files are deleted.** An end-to-end folder holds
  `deployment/` and one `test_*.py`. `deployment/default.nix` gains `pkgs` and `operator` as
  arguments, applies its own packages, and returns the deployment build — the folder still owns every
  fact about its fixture and now owns none of the machinery. The path-escape rule of
  `tests/unit/layers.nix` is why the builder arrives as an argument rather than an import.
- **BREAKING — folders are discovered, not registered.** `flake-module.nix` reads
  `tests/e2e/*/deployment/default.nix` and exposes `packages.planner-e2e-<folder>` for each, so a new
  folder needs no flake edit, as the runner's own discovery already needs none. `e2eArtifactPaths`
  loses its three artifact rows and gains `PLANNER_CLI` and `PLANNER_CLI_SRC`; the guest image
  and the ssh key stay.
- **BREAKING — the harness stops being an operator.** `copy_argv`, `install_argv`, `deliver`,
  `deliver_value`, `activate`, `status`, `rollback` and `ssh_opts` leave `tests/e2e/delivery.py` for
  `cli/`. What stays is what only a test needs: the cluster stage, the ssh key copy, the state
  root, and the plan readers the assertions use. `tests/e2e/test_harness.py` keeps asserting the pure
  half — now the command's ordering and refusals rather than the harness's own argv.
- **Each folder's test applies its deployment with `planner`.** The claims already there are
  unchanged and are now observed through the command an operator runs; the machine layer gains what
  only the command can be asked: an image entry attached by `apply`, a rollback and a status report
  driven by the tool, and a secret applied out of an operator-held value source.

Not in this change, deliberately:

- **Generating, storing, encrypting or rotating a value.** `--values` is a directory of bytes.
  `generate-values-with-nixos-secrets` owns where they come from, and its tasks 1.3 and 1.5 — a fourth
  hand-written `artifacts.nix` and its flake rows — are superseded by this change rather than done.
- **Concurrency.** `apply` walks machines one at a time in a deterministic order. A parallel apply is
  a scheduling question, and nothing here needs it to be answered.
- **Health checks and automatic rollback.** `apply` reports what the endpoint reported. Deciding that
  a deployment is unhealthy and undoing it needs a definition of healthy that no plan field carries.
- **`state.json` and `exports.json`.** Both are absent from the flakelet realiser on purpose
  (`flakelet/default.nix:8-10`) and stay absent.
- **A machine-side agent.** `apply` reaches a machine over ssh and runs the endpoint that is already
  there. Nothing new is installed on a machine.
- **Rewriting the command in Rust.** The tool orchestrates `nix` and `ssh` and walks decoded JSON, in
  a repository that already types and tests Python. D7 records the trigger that would change that.

## Capabilities

### New Capabilities

`operator` is a role rather than a directory, the way `realiser` already covers both `image/` and
`flakelet/`. Its two capabilities are implemented by two directories, and neither imports the other:
`operator/` is evaluated, `cli/` is run.

- `operator/deployment-build` (`operator/`): what building a whole deployment produces, how an
  artifact is addressed, which realiser realises an entry, what the manifest states, and every way a
  build is refused.
- `operator/apply-command` (`cli/`): the operator's own command — the order it applies a deployment
  in, where the bytes of a generated value come from, what it refuses before it dials a machine, and
  what it does on one.

### Modified Capabilities

- `delivery/real-cluster`: the artifacts a run delivers are built by the operator's command and the
  delivery steps are the command's own, so the harness contributes no realisation and no delivery
  logic to what the machine layer observes.
- `tooling/test-layers`: an end-to-end folder's fixture is its declaration; the realisation of it is
  shared, arrives as an argument, and is asserted in the evaluating layer. A folder holds no builder
  and the flake names no folder.
