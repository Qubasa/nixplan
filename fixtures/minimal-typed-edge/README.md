# The consumer half of a typed edge, and nothing else

Design sketch with a working planner behind it. `korora.interface`, `uses`,
`provides`, `wire`, `reach`, the placement surface and `secrecy` are
implemented in `lib/`, and the two files under `plan/` are what that
library produces from `deployment/`: regenerated by hand from
`.#debug.worked.plan` and compared against on every run of the suite by
`tests/unit/plan.nix`. `docs/` is
how to use that library on a deployment of your own. Every file under
`interfaces/`, `modules/` and `deployment/` is evaluated as committed and none
was edited to make the library accept it. The sibling design sketches of the
corpus this folder came out of — instance-as-group, secrets-per-instance,
binary-caches and one-daemon-two-networks — are the reference for the adopted
conventions, remain design sketches, and are not in this repository.

**This folder is a counter-proposal and not a worked example of the adopted
sections.** Every sibling writes an export as the quadruple §32.1 adopted:
`type`, `locality`, `lifecycle`, `secrecy`. The four atoms in
`interfaces/exports.nix` write two fields, `type` and `secrecy`. That is a
proposal to narrow §32.1, it is stated at the declaration and in the last gap row
of `plan/diagnostics.txt`, and no change owns it yet. A reader who wants the
adopted shape should read a sibling; a reader who wants to know what the smallest
useful subset is should read this.

`<pkg>.services.default` is elided here, as it is in three sibling sketches. Only
the corpus's instance-as-group sketch ships the real thing. The shape is one
line, `services.default` bound to the package expression a root imports beside
itself, and `modules/borg-repo/default.nix`
and `modules/borg-push/default.nix` are the roots it would publish. Inside a
root, `services` is keyed by member name, which is a different attrset from the
package's.

## The question this folder answers

The other folders ask what the model needs in order to express a fleet. This one
asks the inverse: given a target that already exists, what is the smallest set of
constructs that changes an outcome? The target is clan-core, and the answer turns
out to be five constructs, because the target already built the other half.

## What the platform has today

clan-core has a typed cross-service edge with a checked producer and an
unenforced consumer.

A service declares which of six registered interfaces it emits, and emitting
one it did not declare is a hard throw with a good message
(`clan-core/lib/inventory/distributed-service/all-services-wrapper.nix:85-102`). Nine
services adopted that half.

The consuming half is `manifest.exports.inputs`, declared at
`clan-core/lib/inventory/distributed-service/service-module.nix:350-353`:

```nix
exports.inputs = mkOption {
  type = types.listOf types.str;
  default = [ ];
  description = "List of export interface this service consumes.";
};
```

It is written by exactly two services, `clanServices/pki/default.nix:11` and
`clanServices/dm-dns/default.nix:14`, both `[ "endpoints" ]`, and it is read by
nothing. Nothing checks it, nothing derives an edge from it, and no diagnostic
mentions it.

What consumers do instead is index one clan-global attrset keyed by the string
`"service:instance:role:machine"` (`clan-core/lib/exports/exports.nix:25`). The shape is
written out in the test suite at `clan-core/lib/exports/test_integration.nix:91`:

```nix
exports."A:::${machine.name}".networking.host
```

and in a real service at `clanServices/pki/default.nix:41`:

```nix
lib.mapAttrsToList (_scopeKey: exportValue: exportValue.endpoints.hosts or [ ]) machineExports
```

That `or [ ]` is the whole finding. With nothing to check a read against, a
producer that was never wired and a producer with nothing to say arrive at the
consumer as the same value, so the author writes a default and the service comes
up configured for zero far ends. The same idiom is at
`clanServices/borgbackup/default.nix:72` and `:235`, and
`clanServices/sshd/default.nix:44`, `:48` and `:49`.

C3 of the corpus's unaddressed register has the measurement: the checked producing half is used
by nine services, the unchecked consuming half by two, and the untyped path —
`clanLib.getPublicValue`, which builds a path into another machine's vars
directory and reads the file — carries 34 call sites across nine services.

Types get used in proportion to what enforces them. That is why the consumer-side
check is load-bearing rather than polish, and it is the only claim this folder
rests on.

## The deployment

A repository on `vault` and three machines pushing to it. `alpha` and `beta` are
ordinary. `gamma` was added this week and its keypair has not been generated yet.

`deployment/instances.nix` is two instances and 34 lines:

```nix
vault-repo = {
  module = borgRepo.services.default;
  settings.server.quota = 500;
  placement.every.server = { machines = [ "vault" ]; };
  wire.clients = { instance = "nightly"; provides = "identity"; };
  exposes = [ "repo" ];
};

nightly = {
  module = borgPush.services.default;
  settings.client.path = "/home";
  placement.every.client = { tags = [ "backed-up" ]; };
  wire.repo = { instance = "vault-repo"; provides = "repo"; };
  exposes = [ "identity" ];
};
```

Two wires and they point at each other. The repository reads every pusher's host
key to authorize it; each pusher reads the repository's URL and quota. The graph
is acyclic for §29.5's reason — a capability's exports are a function of module
and settings and never of a `wire` — so neither entry appears in the other's
`dependsOn` and neither read waits on the other.

The corpus's one-daemon-two-networks sketch keeps its own mutual pair acyclic
a different way, by resolving both reads through the fact register, because both
of its values are `at-most-probed`. Here both values are known at evaluation, so
the pair resolves directly and no register is involved. That is the concrete
payoff of dropping `lifecycle`: a mutual edge between two static providers needs
no plane to stand on.

## The five constructs

| Construct | What it replaces in the target |
| --------- | ------------------------------ |
| an interface is an imported value, `name` is a label | the closed six-entry registry at `modules/clan/top-level-interface.nix:421-427` |
| `provides.<cap> = { interface; }` | `manifest.exports.out`, a list of registry names |
| `uses.<slot> = { interface; reads; }` | `manifest.exports.inputs`, declared and read by nothing |
| `wire.<slot> = { instance; provides; }` | a hand-built string key inside the consuming module |
| a provider's keyset equals its interface's keyset | nothing — an extra key is invisible and a missing one is `or [ ]` |

Every check emits a diagnostic row rather than a throw, and that costs no new
machinery either: the target already carries `{id, message, severity}` records
from `service-module.nix:949-1000` through `modules/clan/distributed-services.nix:170`
to `pkgs/clan-cli/clan_lib/inventory_checks.py:33-48`, where warnings are logged
and errors raise. Today that pipe carries role-count constraints and nothing
else. The wiring checks fit in it as written.

## Why `reach` is in, having been meant to be out

`reach` was going to be deferred. The folder put it back, and the reason is a
property of the target rather than a preference.

In clan-core membership is authored: a role is a set of machines. So a slot
pointing at a role points at a set whether or not anybody says so, and leaving
the field out does not make a read single-valued — it makes the arity something
the reader infers from a machine list in a different file. §31.1 names that
silence, and not the fan-out, as the defect.

Two of its three values are here. `reach = "one"` refuses a single-valued read of
a capability with two placements. `reach = "all"` makes the read an attrset keyed
by machine whose entries are named rather than counted, which is the refusal the
`gamma` row in `plan/diagnostics.txt` is made of. `reach = "local"` is not here,
because `local` emits a co-placement constraint and co-placement is derived from
`locality`, which this folder does not have. The value that needed the machinery
this folder dropped is exactly the value it dropped.

## What is deliberately out, and what brings each one back

Nothing below is argued with. Each one has a trigger, and each trigger is a fact
about the target rather than a judgement about the mechanism.

| Out | Why not now | Trigger to add it |
| --- | ----------- | ----------------- |
| `locality`, and with it §32.2's lattices, §32.4's bound-versus-tag split and §32.5's two dispositions | all six registered export interfaces in the target are readable from anywhere, so the field would admit one value on every atom | the first export whose value is a unix socket path or a loopback port |
| `lifecycle`, and with it probes, facts and the register | everything the target evaluates is build-time static | already met elsewhere: two of twelve mesh sketches of the corpus assign an address only after the daemon authenticates |
| `placement.pick`, `strategy`, stable allocation rows | nothing in this deployment delegates a choice, and `pick` is what makes an otherwise pure planner stateful | the first service whose machine the operator is willing to let the planner choose |
| `members.<name>.enable`, `wire.<member>.<use>` | both roots here have one member and nothing is cut | a module publishing a composition whose coherent cuts an operator wants |
| externals | no non-fleet resource appears here | a non-fleet resource this deployment has to name, which the corpus records as U3 and U4 and neither is closed |
| `collects`, `contributes`, `answers` | see below. This is the one omission that costs a real consumer | `clanServices/pki`, and nothing smaller |
| the whole runtime plane — register, frontier, CAS, host agent, orchestrator | the target deploys by building a toplevel and running switch-to-configuration (`pkgs/clan-cli/clan_lib/machines/update.py:565-566`), and all nine of §24's counter-examples live in this plane | not this change |

## The omission that costs something

`clanServices/pki/default.nix:33` reads

```nix
clanLib.selectExports (scope: scope.machineName == machine.name) exports
```

which is every export on its own machine, from services it does not name and did
not wire. That is a collector. It is §30's subject, and it is the one real
consumer in the target that the surface in this folder cannot convert — which is
pointed, because `pki` is also one of the two services that declares the dead
`manifest.exports.inputs`.

So the honest scope is: this folder finishes the WIRED reads and leaves the
machine-scoped ones alone. The corpus's firewall and quiesce-group sketches own those and
neither is retracted. What this folder does claim is that the wired reads are
where the 34 call sites are, and that §30 — DECIDED and not ADOPTED, with
`collects`, `contributes`, `answers`, `policy.collects` and the `collected`
argument existing in no tree, an authoring bill the firewall sketch calls the
product of services and questions, and a chain whose failure rows name no author
— should not be what a first implementation has to carry.

## What it produces

`plan/backup.json` has all eleven entries the deployment produces: four
placements, the four machines those placements depend on, and the three host-key
values `nightly` generates, one per placement. It elides nothing,
because an evaluator cannot. Two of the eleven are there for the planner rather
than for a reader, and the hand-written version of this file used to name them
and skip them for exactly the reasons that still hold if you are reading rather
than testing: `nightly:client@beta` is field for field `nightly:client@alpha`
with the machine changed, and `machine:beta` is named only by that entry's
`dependsOn`. Read alpha and gamma; beta says nothing a third reading adds.

Every export record carries the `secrecy` its atom declared and nothing else
that an author wrote. The other fields on a record — `plane`, `readBy`, `rows`
— are what the planner resolved about that export. A plan recording a
`locality` here would be recording a field no interface wrote.

`plan/diagnostics.txt` has two rows from this deployment, five counterfactual
rejections and five gap rows. The first row is the folder's whole argument in one
line:

```
! vault-repo:server@vault  clients names three entries and `nightly:client@gamma` has no bytes
```

`gamma` declared its capability, the tag placed it, the entry exists, and only
the bytes are missing, so the row names the machine before anything is deployed
and the apply is blocked. The same mistake in the target is a fold with a default
of `null` and the nulls dropped, so the repository comes up, the server is
healthy, two clients push, and gamma's backup silently never happens.

## The falsifiable claim

One sentence, and it is checkable against files that exist rather than against
this folder:

> Convert `clanServices/pki`'s wired reads — not its machine-scoped one — and
> `clanServices/borgbackup`'s client fold to `uses` plus `wire`, delete the four
> `or [ ]` sites, and removing a producing instance yields a `cliChecks` row
> naming the slot instead of an empty list.

If that diff is not smaller and louder than what it replaces, the subset is wrong
and nothing further should be built on it.
